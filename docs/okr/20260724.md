## 完成事项

1. **完成了 Worker Pipeline 主动注册机制的实现与 debug**。Worker 启动及每 60 秒心跳向 Backend 注册 Pipeline 清单（`POST /api/worker/pipelines/register`），Backend 以 `ConcurrentHashMap` 内存注册表缓存。`createSessionJob()` 在 DB 校验后增加 Worker 注册表交叉检查，`getAvailablePipelines()` 过滤未注册 Pipeline。废弃了依赖本地文件 `pipeline-manifest.json` 的旧读取方式，改为从内存注册表获取。解决了 Python → Java 的 snake_case/camelCase JSON 字段命名不一致问题

2. **完成了 "Unknown pipeline" 错误的全链路根因定位**。通过逐层埋点（后端 DB SQL DEBUG、INSERT 回读验证、Worker claim 响应完整 dump、PIPELINES 注册表 hex 对比）发现了两个根因：
   - **MyBatis-Plus `selectOne` + `.last("LIMIT 1")` 与 `selectCount` 返回不一致**：相同 WHERE 条件下 selectOne 返回 0 行而 selectCount 返回 1，改用 `selectList + get(0)` 绕过
   - **Pipeline ID 在 DB（MySQL 大小写不敏感存储）与 Python dict（大小写敏感）之间存在不一致风险**：MySQL VARCHAR 比较默认不区分大小写，可能导致 `"g1_merge_camera_robot"` 写入 DB 但 Worker 的 `PIPELINES` dict 只有 `"G1_MERGE_CAMERA_ROBOT"`

3. **完成了 Pipeline ID 的规范化防御**。在 Java 侧新增 `PipelineIdNormalizer`（strip + uppercase），在 `createJob`/`createManualJob`/`createSessionJob` 的入口统一规范化 pipelineId。Worker 端在 `claim_job()` 返回的 pipelineId 同样做 strip + uppercase 处理，确保两边对齐。Worker 端 `PIPELINES.get()` 失败时增加 case-insensitive 兜底匹配

4. **完成了 Worker 端健壮性增强**。新增 `retry_http()`（指数退避 1s/2s/4s，最多 3 次重试）覆盖 claim/success/failure 请求，新增 `_oss_retry()`（4 次尝试）覆盖 OSS 下载/上传操作；Worker 主循环新增 `try/except Exception` 保护，防止未预期异常导致静默退出

5. **完成了 CLAIMED 卡死作业的自动恢复**。新增 `@Scheduled(fixedRate = 60000)` 定时任务，检测被 CLAIMED 超过 5 分钟的作业（Worker 崩溃/重启导致未上报成功或失败），自动重置为 CREATED 状态，防止作业永久卡死

6. **完成了 G1_CONVERT_TO_LEROBOT Pipeline 的 Windows 兼容修复**。修复了 `LeRobotDataset.create()` 在 Windows 下遇已存在 `output_dir` 抛 WinError 183 的问题（调用前 `os.rmdir` 移除空目录），修复了产物文件收集路径过于严格导致漏扫的问题（改为扫描 `output_dir` + 扩展名白名单兜底 + 无产物时打印完整目录树）

7. **完成了启动顺序要求的文档化**。在 `CLAUDE.md` 和 `deploy.md` 中明确了"Backend 必须先于 Worker 启动"的要求，说明了 Worker 注册机制和 60s 心跳重试的容错窗口。更新了故障排查表新增前端报错和 Unknown pipeline 的排查条目

8. **完成了全链路诊断日志的添加与精简**。在排查过程中增加了约 80 行诊断日志（SQL DEBUG、INSERT 验证、claim 响应 hex dump、Unknown pipeline ASCII 表格诊断等），定位根因后全部精简至保留核心运维日志（创建/领取/成功/失败一行日志），移除了冗余的 hex 编码、统计计数、SQL DEBUG 配置

# 2026-07-24 工作总结：前端页面加载性能分析与优化方向梳理

## O（object，待办版本）

1. 完成采集详情页、会话详情页、数据处理页的加载链路分析
2. 定位页面加载慢的根因并输出优化方案

## 完成事项

1. **完成了三个核心页面的全链路加载分析**。逐层拆解了 AcquisitionDetailView（/acquisition/:taskId，5 个 API）、SessionDetailView（/sessions/:sessionId，9 个 API）、ProcessingTemplateView（/processing，3 个 API + 5 秒轮询）的 onMounted 调用链，从 Vue 组件 → API 封装层（platform.ts / processing.ts / sessions.ts）→ 后端 REST 端点完整追踪，并输出每个页面的调用树状图

2. **定位了页面加载慢的三个根因**：
   - **每次详情页都拉全量 500 条 sessions**：`fetchSessionDetail()` 实际调用 `fetchAllSessions()`（`GET /api/sessions?pageSize=500`），在浏览器端用 `sessions.find()` 过滤出目标 session，而非后端提供单条详情接口。数据量增长后网络传输和 JSON 解析耗时线性增加
   - **`fetchTaskWorkspace` 拉全量 assets/jobs/reports 再前端聚合**：即使只看一个 task，也拉取该 task 下的全部 assets、jobs、reports，在 `buildSessionRecords`、`mapAssetsForSession` 中遍历全量数组做 filter/map 聚合，数据量大的 task 时 JS 主线程阻塞
   - **SessionDetailView 请求链未全并发**：`loadDetail()` 先 `await fetchSessionDetail()` 拿到 `session.id` 后才发后面 5 个 API（availablePipelines、sessionJobs、playbackCheck、sessionFiles、annotationProgress），但 sessionId 可从路由参数直接获取，浪费了并发机会

3. **输出了分层优化方案**：
   - 高优先级：后端新增专用详情聚合 API（`GET /api/sessions/{id}/detail`、`GET /api/tasks/{id}/detail`），请求数从 9→2，数据量降 90%+
   - 中优先级：前端 `SessionDetailView.loadDetail()` 将后 5 个 API 改为与 `fetchSessionDetail` 全 `Promise.all` 并发（不改后端，延迟降低 30-50%）；`fetchAllSessions()` 加 Pinia 缓存避免同页切换重复拉取
   - 低优先级：Processing 页轮询改为条件轮询（有 RUNNING/CREATED 状态才继续，全终态则停）

## 下步计划

1. 后端新增 Session 详情聚合 API，返回单 session 的 assets/jobs/reports 而非全量数据
2. 前端 `loadDetail()` 并发化改造，将 sessionId 从路由参数取值使后续请求可提前发出
3. 评估是否需要为 AcquisitionDetailView 同样增加后端聚合 API
